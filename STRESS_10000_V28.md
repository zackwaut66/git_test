## Stress architecture

The first stress implementation attempted to keep all 10,000 profiles inside one Chromium process. It was functionally valid but unnecessarily slow and created a risk that the test runner itself, rather than the game systems, would become the limiting factor.

The final gate therefore uses a 10-job matrix. Each isolated Chromium job executes 1,000 complete profiles, for exactly 10,000 profiles total. `fail-fast` is disabled so every batch runs even if another batch encounters a problem. Each batch uploads its own JSON report for diagnosis.

This structure is now the preferred large-run validation method for future background-mechanics changes.

The stress gate fails only when the game reaches an invalid state, becomes unable to progress under the permitted retry budget, loses persistence integrity, produces a browser/runtime error, or violates a tested invariant.
